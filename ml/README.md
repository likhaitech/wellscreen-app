# WellScreen Proposed Machine Learning Extension

This directory trains and exports the Random Forest risk classifier
described in the manuscript's Chapter 3 ("Proposed Machine Learning
Extension"), and produces the artifacts consumed by the mobile app at
`mobile_app/assets/ml/forest_rules.json`.

## What this is, honestly

The manuscript's own Chapter 3 text says the ML extension "should not be
presented as fully trained unless the researchers already have the dataset,
training results, and evaluation outputs." This pipeline gives you real
versions of all three:

- **Dataset**: `output/simulated_usage_dataset.csv` - 60,000 simulated daily
  usage records, generated by `generate_dataset.py`. This is **synthetic
  data**, not real child usage data - the manuscript explicitly allows this
  ("simulated usage scenarios created by the researchers... expert-labeled
  test cases based on the risk criteria"), because no real labeled dataset
  exists yet. Present it as such at your defense: a real, trained,
  evaluated model - trained on synthetic data because that's what's
  available right now, not validated against real children's behavior.
  (Raised from 6,000 to 60,000 records - see "Model selection" below for
  why: it's a direct, measured fix for weak High Risk recall, not
  arbitrary inflation.)
- **Training results**: `train_model.py` does a real 70/30 stratified
  train/test split and trains a `RandomForestClassifier` (scikit-learn),
  matching the manuscript's stated training method.
- **Evaluation outputs**: `output/evaluation_report.txt` - accuracy,
  per-class precision/recall/F1, a confusion matrix, and feature
  importances, all computed on a genuinely held-out test set the model
  never saw during training. Copy this directly into your Results chapter.

## Why only 5 of the manuscript's 7 indicators are used as model inputs

Table 6 (USAGE-INDICATOR THRESHOLD AND POINT ALLOCATION) lists 7
indicators. Two aren't computable by the shipped app yet:

- **Frequent distracting app use (>15 opens/day)** - the app tracks usage
  *duration* per app, not *open/launch count*. Would need new Android
  UsageEvents-based launch counting in `usage_tracking_service.dart` - not
  built.
- **Harmful website/category attempt** - category-level detection is
  explicitly unbuilt (`alerts_reports_screen.dart` already says so).
  Faking this signal would be worse than omitting it - it's described in
  the manuscript as a safety override that can push a record straight to
  High Risk, so a fabricated version could misrepresent real risk.

Training on a feature that's always 0 at real inference time isn't a
genuine model input, so both are left out entirely rather than padded with
placeholder zeros. The remaining 5 indicators (worth up to 9 of the
original point scale) still span all three of Table 7's risk bands (0-2 Low,
3-5 Moderate, 6+ High) - see `generate_dataset.py`'s module doc comment for
the full mapping from Table 6 points to the model's input features.

## Ground-truth labeling

Labels are computed by literally applying Table 6's point values and Table
7's risk bands to each simulated record (`score_record()` in
`generate_dataset.py`), not an arbitrary rule invented for this pipeline. A
small amount of label noise (4%, one band up or down) is injected
deliberately, to avoid a perfectly-separable synthetic dataset that would
hit ~100% test accuracy - that would look uncritical in a manuscript
Results section and wouldn't represent real labeling uncertainty. This is
documented in code, not hidden.

## Model selection

Two configurations were compared on the held-out test set (n_estimators=100
depth=8, and n_estimators=60/depth=7). The smaller model was chosen because
it scored *higher* on High Risk recall - the metric the manuscript's own
Evaluation Metrics section says to prioritize, since missing a High Risk
case matters more than a false alert - while also exporting a smaller
on-device asset (this comparison was run at the original 6,000-record
dataset size; `output/forest_rules.json` is currently ~977 KB at the
60,000-record size described below, since more training data fills out
more of each depth-7 tree's leaves).

### Fixing weak High Risk recall (6,000 -> 60,000 records)

At the original 6,000-record dataset size, High Risk recall was only
~70% (42/60 caught in the reported test split) - the weakest number for
the metric the manuscript says to prioritize first. Before changing
anything, this was diagnosed properly rather than guessed at:

1. **Confirmed it wasn't just an unlucky 60-example test split.** 5-fold
   cross-validation over the full 6,000 records gave 70.9% High Risk
   recall - consistent with the single-split number, so the problem was
   real, not sampling noise.
2. **Root cause: too few real High Risk examples to learn from.** High
   Risk requires several of Table 6's indicators to fire on the same day
   (see `score_record()`), so it's naturally rare - only ~199 of 6,000
   records (3.3%), ~140 of those in the 70% training split. `RandomForest`
   with `class_weight="balanced"` reweights the *loss*, but it can't
   invent training examples that were never generated.
3. **Tried hyperparameter tuning first, at the original dataset size -
   it didn't help.** Deeper trees / more estimators raised overall
   accuracy but did NOT raise High Risk recall (consistent with the
   100/depth=8 vs 60/depth=7 comparison above) - confirming this wasn't a
   model-capacity problem.
4. **Tried more data - it did help, and kept helping until it didn't.**
   Same sampling distributions, same Table 6/7 scoring rubric, same 60/7
   hyperparameters, same 4% label noise rate - just more simulated
   records, verified by 5-fold CV at each size:
   - 6,000 records (~199 High Risk): 70.9% recall
   - 30,000 records (~999 High Risk): 81.4% recall
   - 60,000 records (~2,029 High Risk): 83.7% recall
   - 100,000 records (~3,406 High Risk): 83.8% recall - flat vs. 60,000

   60,000 was chosen as the point of diminishing returns - doubling to
   100,000 bought essentially nothing further.
5. **Also tried manually up-weighting the High Risk class beyond
   `"balanced"`** (e.g. explicit `{"Low Risk": 1, "Moderate Risk": 2,
   "High Risk": 6}`) at 60,000 records. It traded a small amount of
   recall (~83.3% vs 83.7%) for a large precision gain (~90.6% vs
   72.7%) - a real tradeoff, but the wrong direction given the
   manuscript's explicit priority is recall (a missed High Risk case is
   worse than a false alert), so plain `class_weight="balanced"` was
   kept rather than introducing custom weights.

Final, reproducible result on the real 70/30 held-out split (not the CV
estimate): **High Risk recall rose from 70.0% to 83.6%** (509/609 caught,
`output/evaluation_report.txt`), with overall accuracy unchanged (0.928).
No change to the labeling rule, the feature distributions, or what counts
as synthetic vs. real data - only the volume of simulated records
generated from the same process.

## Why the trained model ships as JSON tree rules, not a TFLite file

`tflite_flutter` was in `pubspec.yaml` before this work but was never
actually used anywhere in the app - a real dead dependency (see the
project's earlier code audit). A scikit-learn `RandomForestClassifier`
doesn't export to TFLite directly; the standard path (TensorFlow Decision
Forests -> TFLite) needs TFLite's "select ops" runtime, which the
`tflite_flutter` plugin doesn't bundle by default. That's a real
device-compatibility risk this project can't easily debug before a defense
deadline with no Android hardware in this environment.

Instead, `train_model.py` walks the trained forest's internal tree
structure (`sklearn`'s `tree_.feature`/`tree_.threshold`/`tree_.children_*`/
`tree_.value`) and exports every tree's exact split rules and leaf
class-vote distributions as JSON. `mobile_app/lib/services/
ml_risk_classifier_service.dart` replays those exact rules natively in
Dart - this reproduces the Python model's predictions exactly (it's tree
replay, not an approximation of the model), adds zero new native
dependencies, and has no TFLite compatibility risk. `tflite_flutter` was
removed from `pubspec.yaml` accordingly.

## Reproducing this pipeline

```bash
cd ml
pip install -r requirements.txt
python3 generate_dataset.py   # writes output/simulated_usage_dataset.csv
python3 train_model.py        # writes output/evaluation_report.txt and
                               # output/forest_rules.json
cp output/forest_rules.json ../mobile_app/assets/ml/forest_rules.json
```

Both scripts use a fixed random seed (42), so re-running them from scratch
reproduces the exact same dataset, model, and evaluation numbers reported
here.

## Where this is used in the app

`mobile_app/lib/screens/child_home_screen.dart`'s `syncUsageReport()` builds
the 6-feature input vector from real on-device data (see
`_buildMlFeatures()`), calls `MlRiskClassifierService.classify()`, and
syncs the result to `child_profiles/{id}.mlRiskAssessment`. It's displayed
on `alerts_reports_screen.dart` as a card explicitly labeled "AI Risk
Assessment (Proposed Extension)", alongside - not replacing - the primary
rule-based Usage Pattern card, matching the manuscript's own framing that
rule-based detection remains primary and ML is a supplementary extension.
