# WellScreen Site-Category Dataset (Harmful Website/Category Detection)

This directory holds a **real, third-party, publicly sourced dataset** used
to prototype the "harmful website/category attempt" indicator from the
manuscript's Table 6 (worth 3 points, the single highest-weighted usage
indicator). It is a separate effort from `ml/` (the usage-pattern risk
classifier) and uses a completely different kind of data - domain names
labeled by category, not usage statistics.

## Why this exists, and what it honestly does and doesn't prove

Two things were unclear before this work, and are worth stating plainly:

1. **UPDATE - URL capture, exact-match detection, AND a live ML classifier
   all now exist.** When this README was first written, WellScreen
   captured no browsed URLs at all, and later, captured URLs weren't
   checked against anything. Both are done now: `BrowserUrlExtractor.kt`/
   `BrowsingLogger.kt` and `WellScreenAccessibilityService.kt`'s
   `maybeCaptureBrowserUrl()` capture the domain from the browser's
   address bar; `SiteCategoryService` checks it against the real cleaned
   dataset below, and - since that lookup can only catch a domain it has
   literally seen before - falls back to a real, trained, evaluated ML
   text classifier for domains it hasn't (see "Live ML classifier" section
   below). Both surface on the "Recent Browsing Activity" card in
   `alerts_reports_screen.dart`. Still **not** built: real-time blocking -
   detection happens at the next sync, after the page has already loaded.
2. This is real data (not generated by this project), which is what makes
   it a genuine data-cleaning exercise - unlike `ml/generate_dataset.py`'s
   synthetic usage data, which has no real-world messiness to clean.

## Source

[UT1 Blacklists](http://dsi.ut-capitole.fr/blacklists/index_en.php),
maintained by Fabrice Prigent at Universite Toulouse Capitole. This is a
long-running, real project used by actual schools/universities for web
filtering - domains are manually reviewed and categorized, not generated.
Mirrored daily at [github.com/olbat/ut1-blacklists](https://github.com/olbat/ut1-blacklists),
licensed CC BY-SA 4.0 (attribution required, which this README provides).

Raw files in `raw/` were fetched directly from that mirror on the date
this was built (see git log for the exact date) and are committed
unmodified, so the "before cleaning" state is reproducible and verifiable
against the source.

### Categories included, and why

| Category | Source | Rows (raw) | Maps to |
|---|---|---|---|
| `gambling` | UT1 (`gambling`) | 32,247 | Table 6 "harmful website/category" |
| `drugs` | UT1 (`drogue`, 603) + The Block List Project (`drugs.txt`, 26,029) | 26,650 combined | Table 6 "harmful website/category" |
| `dangerous_material` | UT1 | 35 | weapons/explosives instructions; also includes a couple of pro-eating-disorder domains, which are self-harm-adjacent |
| `adult` | Philippines NTC enforcement (NOT UT1) | 3 | Table 6 "harmful website/category", with local (PH) relevance |

**Why `drugs` has a second source:** UT1's own `drogue` list is small
(603 raw domains) - too small, on its own, to train a reliable ML
classifier (see "Live ML classifier" below). Checked directly against
UT1's live mirror before assuming this: UT1's `drogue` category is
genuinely only 603 domains (+464 page-level `urls` entries, which are
individual pages on generic hosting platforms like webring.org,
geocities.com, tripod.com - not domain-level data, and mostly NOT
harmful domains themselves, so deliberately NOT used here - see "What
was checked and rejected" below). To get a real, meaningfully larger
`drugs` dataset, a second, independently-maintained source was added:
[The Block List Project](https://github.com/blocklistproject/Lists)'s
`drugs` list (26,029 domains, MIT licensed, updated regularly, used by
real Pi-hole/AdGuard Home installs for household-level content
filtering). Checked before adding: overlap with that same project's own
malware/phishing/scam/fraud/ransomware lists is under 1% (243 of 26,029
domains), confirming this is a genuinely distinct "drugs" category, not
a relabeled slice of generic threat-intel noise. See
`raw/drugs_domains_blocklistproject.txt` for the full sourcing header
and an honest note on what kind of "drug-related" content this list
actually contains (mostly illicit/counterfeit online pharmacy spam
networks, not drug-culture/information sites - which is why a lot of the
domains look like algorithmically generated strings rather than readable
words).

**What was checked and rejected for `dangerous_material` (weapons/
explosives):** before adding more UT1 data alone, UT1's live mirror was
checked directly - `dangerous_material` is genuinely only 35 domains (+
19 page-level `urls` entries, same generic-hosting-platform problem as
above: e.g. `membres.lycos.fr`, `pageperso.aol.fr`, `angelfire.com` -
pages on shared free web hosts that host dangerous-material content
somewhere on the platform, not domains that are themselves about
weapons/explosives; treating the platform's own domain as "dangerous
material" would be a real false-positive risk in an ML training set).
Multiple open, actively-maintained categorized blocklists were then
searched for a domain-level weapons/explosives/firearms category - The
Block List Project (18 categories, no weapons/explosives category),
HaGeZi's DNS blocklists, and general web search for a dedicated
firearms/explosives domain blocklist - **none were found.** Unlike
gambling/drugs/pornography, a domain-level weapons/explosives blocklist
doesn't appear to be something the open DNS-filtering community
maintains at scale. This is reported honestly as a real, searched-for-
and-not-found gap, not an assumption: `dangerous_material` stays at 35
real domains, exact-match-lookup-only (see "Live ML classifier" below
for why it's excluded from the ML fallback too).

**Deliberately excluded:** UT1's own `adult` category (4.6 million domains
- not practical to store or ship as a mobile asset for a school project,
and not needed to demonstrate the cleaning methodology). A production
version would add it from the same source, the same way.

**The `adult` category actually included here is different, and much
smaller.** It is NOT from UT1 at all. It's 3 domains
(pornhub.com, xvideos.com, redtube.com) individually named in real
Philippine news coverage of the NTC's January 2017 order blocking
pornography sites under Republic Act 9775 (the Anti-Child Pornography
Act) - researched via live web search when this was added, not guessed.
Stated honestly: **no comprehensive, official Philippines domain
blocklist exists publicly** for either pornography or illegal online
gambling - multiple independent sources explicitly confirm this (see
citations in `raw/adult_domains_philippines.txt`). PAGCOR has reported
detecting hundreds of illegal gambling sites and NTC has reported
blocking sites in bulk, but neither has ever published the actual domain
list - only counts. So this 3-domain set is real and properly sourced,
but it is NOT a Philippines-scale dataset, and shouldn't be presented as
one. It exists to make the dataset locally relevant, not to claim
Philippines coverage it doesn't have.

**Honest gap:** UT1 has no dedicated self-harm/suicide category. That
part of Table 6's indicator isn't covered by this dataset. A keyword-based
approach (similar to `PatternDetectionService`'s existing `riskyKeywords`
list, which already does rule-based text matching) is a more realistic
path for that specific risk than a domain blocklist, since self-harm
content usually shows up on mainstream sites/forums rather than
dedicated, blockable domains. Not built here - flagged for a future
session.

## Cleaning methodology

`clean_dataset.py` runs these steps on each raw category file, in order,
and logs the result of every step:

1. Strip whitespace, drop blank lines and comment lines (`#`, `//`).
2. Take only the first whitespace-separated token per line (guards
   against stray trailing comments on a data line).
3. Detect and remove entries that are IP addresses rather than domain
   names (`ipaddress` stdlib) - a blocklist keyed on domain name can't
   match against a bare IP the same way, so these need separate handling
   this project doesn't do yet, and are logged rather than silently kept.
4. Validate the remaining tokens against a permissive FQDN pattern;
   anything that doesn't look like a real domain is rejected and logged.
5. Deduplicate within each category.
6. Deduplicate across categories (a domain listed under more than one raw
   file keeps its first-encountered category; every conflict is logged
   rather than dropped silently).

Every count above is real output from running the script against the
actual raw files, not estimated. Full numbers are in
`output/cleaning_report.txt`, regenerated each run.

### What the cleaning actually found

Run against the current raw files (UT1's three sources, The Block List
Project's `drugs` list, and the small `adult` source): 743 of 58,969 raw
rows (1.3%) were removed. The large majority of that comes from the new
`drugs` source specifically - 167 IP-address entries, 280 malformed
entries (mostly long algorithmically-generated spam subdomains containing
underscores, which the FQDN pattern correctly rejects - e.g.
`...konto_identity.vorkehrung.tk`), and 230 in-category duplicates (real
overlap between UT1's `drogue` list and The Block List Project's `drugs`
list, safely deduplicated rather than double-counted). `gambling` lost 14
IP-address entries. For the `adult` source, 17 of its 20 raw lines were
removed - but that's expected, not a data problem: those lines are the
source-citation header comments written into
`raw/adult_domains_philippines.txt` (the cleaning script correctly strips
`#`-prefixed lines the same way it would for any comment), leaving
exactly the 3 real domains. Zero domains overlapped across the four
final categories. That's a legitimate finding, not a shortcoming of the
cleaning script: both UT1 and The Block List Project are mature,
actively-maintained projects, so their lists arrive fairly clean already.

**Known limitation worth flagging in your Results/Limitations section:**
the final dataset is still imbalanced - `gambling` is 32,233 of 58,219
rows (55.4%), `drugs` 25,948 (44.6%, after adding the second real
source), `dangerous_material` 35, `adult` only 3. `class_weight="balanced"`
addresses this for the ML classifier (see "Live ML classifier" below).
For the pure domain-lookup implementation, the imbalance doesn't matter
at all - the app checks against the whole list regardless of category
size. `dangerous_material` (35) and `adult` (3) remain small - both are
real, sourced, and honestly documented as non-comprehensive (see above
for what was checked and why no larger real source exists for either).

## Live ML classifier (category_classifier, on top of the lookup above)

The exact-match lookup above can only ever catch a domain that is
literally a row in `cleaned_site_categories.csv`. `train_category_classifier.py`
trains a genuine, separate machine learning model on top of it - a
character n-gram TF-IDF + multinomial LogisticRegression text classifier,
run live on-device in the app - so a domain the lookup has never seen can
still be caught if it *looks* like a gambling site. This is a real ML
model trained on real data (not a lookup table, and not synthetic data
like `ml/generate_dataset.py`'s usage-risk dataset), evaluated the same
rigorous way as the risk classifier in `ml/train_model.py`.

**What it's trained on:** `output/ml_training_dataset_with_safe.csv` -
78,177 real domains: the 58,219 harmful ones above, plus 19,958 real
"safe"/benign domains from DNSFilter's public top-domains-by-real-DNS-
query-volume list (github.com/DNSFilter/topdomains, CC-equivalent public
data, fetched August 2026 - see `raw/safe_domains_dnsfilter_raw.txt` for
full sourcing). `safe` is NOT a Table 6 harmful category and the app
never alerts on it - it exists purely as a negative-example training
signal.

**Why the safe class exists - an honest account, not a footnote:** the
first version of this classifier was trained on the harmful categories
only, with zero negative examples. Live testing found it then predicted
"gambling" (some with 90%+ confidence) for completely unrelated real
sites - slack.com, trello.com, duolingo.com, amazon.com, target.com -
because it had never once seen what an ordinary domain looks like and was
forced to guess a harmful label for everything it was shown. Adding the
real safe class was the actual fix, not a threshold adjustment.

**Deployment decision, backed by measurement, not intuition - including a
deliberate attempt to break it before trusting it:** even with the safe
class, a genuinely held-out validation set (`validation/
safe_domains_heldout.txt` - 200 real domains, ranked 20,001-20,200 on the
same DNSFilter list the training "safe" class was built from ranks
1-20,000, never used in training) still produced false positives below a
0.90 confidence threshold. At 0.90, **0 false positives were observed
across all 200 held-out domains**, and `gambling` catches 89.3% of real
gambling test domains at that bar (measured on a genuinely held-out
20%-stratified split, 6,447 real examples) - `gambling` is trusted in
`LIVE_DEPLOYMENT_CLASSES`.

`drugs` was tested for the same bar after its dataset grew from 436 to
25,948 real examples (see "Why `drugs` has a second source" above), and
initially looked just as safe: still 0/200 false positives on that same
easy holdout, plus 61.3% recall on 5,191 real held-out drugs test
examples - both statistically meaningful numbers. **Before trusting
that, a harder, more targeted real-domain test was built on purpose**
(`validation/safe_pharmacy_health_heldout.txt` - 27 real, legitimate
pharmacy/healthcare companies: goodrx.com, cvs.com, webmd.com,
truepill.com, and others), because a large share of the new drugs
training data is illicit online-pharmacy spam, so "pharmacy/rx-shaped"
character patterns are exactly what the model learned to associate with
`drugs` - a pattern a legitimate pharmacy-delivery startup's domain
would also match. **This harder test caught a real problem the easy one
missed:** at the same 0.90 threshold, `truepill.com` - a real, legitimate,
well-known US pharmacy company, not fabricated - was predicted `drugs`
at 95.5% confidence, comfortably above the deployment bar (1 of 27
domains tested, 3.7%; even 0.95 doesn't clear it). That's a concrete,
reproducible failure mode a skeptical reviewer could trigger by typing a
real pharmacy startup's domain into the app, not a hypothetical one.
**Decision: `drugs` stays OUT of `LIVE_DEPLOYMENT_CLASSES`**, even though
it passed the easier check - the much larger real dataset still benefits
the app through the exact-match lookup (25,948 real drugs domains now,
up from 436), just not yet through ML generalization to domains the
lookup hasn't seen. `dangerous_material` and `adult` stay excluded from
live deployment entirely too - not just threshold-gated - because those
classes have far too few real training examples (35/3): 0% recall at the
0.90 bar on their own held-out test examples (7 and 1 respectively),
measured, not assumed, and no larger real domain-level source was found
for either after searching (see "What was checked and rejected" above).

### Cleanup attempt: did fixing known-mislabeled training data resolve the false positive?

After the `truepill.com` finding above, `clean_dataset.py` was updated to
remove 7 domains from the `drugs` training data that were individually
verified to be genuinely legitimate sites mislabeled by the raw source
files - `drugs.com`, `pharmacychecker.com`, and `rxlist.com` (all
legitimate drug-reference/price-comparison sites), plus 4 university
health-education resources (`cesar.umd.edu`, `chemweb.calpoly.edu`,
`goaskalice.columbia.edu`, `prohibition.history.ohio-state.edu`). See
`KNOWN_MISLABELED_LEGITIMATE_DOMAINS` in `clean_dataset.py` for the full
verification method (every `.gov` and `.edu` entry in the raw drugs data
was checked; ~85 well-known legitimate pharmacy/health/pharma/government
domain names were checked by name against the raw files; a spot-check of
several hundred `.org`/`.info` entries confirmed the overwhelming
majority are genuine illicit-pharmacy-spam-pattern domains, not further
undiscovered legitimate sites).

**Honest result after retraining on the cleaned data: this did NOT fix
the problem.** `truepill.com` still predicts `drugs` at 95.1% confidence
(barely moved from 95.5%) - still above the deployment bar. Removing 7
domains out of 25,955 training examples was never likely to move a
model's decision boundary much on its own, and it didn't.

**Why, diagnosed rather than assumed:** re-running the general 200-domain
safe holdout after the cleanup surfaced a *new* false positive that
wasn't there before - `odnoklassniki.ru` (a real, major Russian social
network, unrelated to drugs in any way) predicted `drugs` at 90.2%
confidence. That's a different kind of failure than the pharmacy-naming
one: `.ru` and `.su` domains make up roughly 34% of the raw drugs
training data (5,809 + 3,114 of 26,667 raw lines, mostly illicit online-
pharmacy spam hosted in those TLDs), so the classifier has learned a
broad TLD-level association ("`.ru`/`.su` domains tend to be drugs
sites") on top of the pharmacy-naming association - neither of which is
fixable by removing a handful of individually mislabeled rows. The real
fix would need to address the training data's TLD imbalance directly
(e.g. down-weighting or capping how much any single TLD can dominate the
`drugs` class) or engineering features that don't let the model key off
TLD alone - a larger change than a cleaning pass, not attempted here.

**What this cleanup pass IS worth keeping for:** the 7 removed domains
are genuinely, verifiably mislabeled, and removing them is correct
regardless of the ML outcome - it means the exact-match lookup (Table 20
in the manuscript) can never flag `drugs.com`, `pharmacychecker.com`,
`rxlist.com`, or the 4 university resources as harmful if a child's
device ever visits them, which is a real, direct correctness
improvement. It also means the "safe" training class picked up 2 of
those domains as genuine safe examples (`drugs.com` and `rxlist.com` are
present in the DNSFilter safe source too - previously dropped entirely
as a harmful/safe conflict; now correctly labeled `safe`), which is a
second small, real improvement to data quality independent of the ML
deployment question. `drugs` staying out of `LIVE_DEPLOYMENT_CLASSES` is
unchanged - now for a more precisely understood reason (broad
naming/TLD-pattern bias in the source data, not a short list of bad
labels) rather than a less-diagnosed one.

Full numbers for all of this: `output/category_classifier_evaluation.txt`
(regenerated by `train_category_classifier.py`, includes the full
threshold sweep on both held-out sets and the per-class
recall-at-deployment-threshold check - this file is reproducible, not
hand-edited). Stated honestly: 0/200 observed on the easy set is not a
mathematical guarantee of 0% real-world false positives even for
`gambling` - it means the true rate is very likely low, not that it is
zero, which is exactly what the harder pharmacy-domain check on `drugs`
demonstrated in practice.

**Where it actually runs:** `mobile_app/lib/services/
site_category_ml_classifier.dart` is a hand-written, faithfulness-verified
port of the trained model's math into pure Dart (this app has no ML
runtime like TFLite - see that file's doc comment for why this specific
model shape was chosen so it could be ported by hand at all, and for how
the port was verified against sklearn's actual output before being
trusted). `SiteCategoryService` (`site_category_service.dart`) tries the
exact lookup first, then the keyword layer described below, and only
falls back to this classifier - gated to `gambling`-only predictions
above the 0.90 bar - when both of those find nothing. A match from any
mechanism is tagged with its source (`lookup`, `keyword`, or `ml`) so the
parent-facing UI can show which one caught it (`alerts_reports_screen.dart`
shows "(keyword match)" for keyword matches and "(AI-detected)" for ML
matches).

## Keyword-based pornography detection (manuscript-aligned layer)

Our manuscript describes pornography detection specifically as keyword
matching against the domain (terms like "porn", "xxx", "sex", "tube") -
a different, simpler technique than the ML classifier above. Rather than
quietly substituting the ML approach everywhere, `mobile_app/lib/services/
adult_keyword_detector.dart` implements what the manuscript actually
describes, as a real, tested detection layer (not just documentation
text) - so this is defensible if a panelist checks the running app
against the manuscript's claim.

**Design decisions, tested empirically rather than assumed:**

- **Substring matching, not word-boundary matching.** The codebase
  already had a word-boundary keyword matcher
  (`PatternDetectionService.riskyKeywords`/`_matchesKeyword()`, used for
  app package/display names). Reusing it for domains was tried first and
  rejected: real pornography domains are overwhelmingly compound names
  (pornhub.com, youporn.com, xvideos.com) where the keyword is fused with
  other letters, not an isolated token - word-boundary matching missed 7
  of 10 realistic test domains. Substring matching catches these; it
  raised recall to 9/10 on the same test set.
- **A curated safe-domain allowlist**, checked before any keyword match,
  to mitigate the well-known "Scunthorpe problem" that substring matching
  reopens (e.g. youtube.com contains "tube"; essex.ac.uk / sussex.ac.uk /
  middlesex.gov.uk / wessex.com contain "sex" as part of a UK place name,
  not a live word). With the allowlist in place, testing found 0 false
  positives across a 25-domain curated tricky set and the full 200-domain
  real held-out safe validation set used for the ML classifier above.
- **No bare "x" keyword**, even though early drafts of the manuscript
  wording implied one. The real domain for X (formerly Twitter) is
  literally x.com - one of the most-visited sites on Earth. "xxx" is used
  instead: it's the actual industry convention for adult content (`.xxx`
  is a real reserved top-level domain for it) and does not collide with
  an unrelated massive real domain the way bare "x" would.

**Honest limitation, not hidden:** an allowlist can never be complete. A
legitimate domain not yet on the list that happens to contain one of
these substrings could still false-positive. This is a known, inherent
property of keyword/substring matching generally, not a flaw unique to
this implementation - which is exactly why the ML classifier above is
validated differently (a measured false-positive rate against real
held-out data) rather than relying on an allowlist. The two layers make
different, honestly different guarantees, and neither doc comments nor
this README overclaim ML-level statistical rigor for the keyword layer.

**Reproducing the classifier:**

```bash
cd ml/site_category
python3 clean_dataset.py               # builds output/ml_training_dataset_with_safe.csv
python3 train_category_classifier.py   # trains, evaluates, exports weights JSON
```

Deterministic (`random_state=42` throughout) given the same raw files.
Writes `output/category_classifier_evaluation.txt` and
`output/category_classifier_weights.json` (the latter is copied into
`mobile_app/assets/site_categories/` and must be re-copied there any time
the model is retrained, since it's a build artifact, not source).
