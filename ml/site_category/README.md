# WellScreen Site-Category Dataset (Harmful Website/Category Detection)

This directory holds a **real, third-party, publicly sourced dataset** used
to prototype the "harmful website/category attempt" indicator from the
manuscript's Table 6 (worth 3 points, the single highest-weighted usage
indicator). It is a separate effort from `ml/` (the usage-pattern risk
classifier) and uses a completely different kind of data - domain names
labeled by category, not usage statistics.

## Why this exists, and what it honestly does and doesn't prove

Two things were unclear before this work, and are worth stating plainly:

1. **UPDATE - URL capture now exists.** When this README was first written,
   WellScreen captured no browsed URLs at all. That's since been built -
   see `BrowserUrlExtractor.kt`/`BrowsingLogger.kt` and
   `WellScreenAccessibilityService.kt`'s `maybeCaptureBrowserUrl()`, which
   reads the address bar of supported browsers and logs the domain,
   surfaced on the "Recent Browsing Activity" card in
   `alerts_reports_screen.dart`. What's still **not** built is the other
   half: nothing yet checks a captured domain against this dataset or
   blocks/alerts on it. Capture and classification are still two separate
   pieces of work; only the first one is done.
2. This is real data (not generated by this project), which is what makes
   it a genuine data-cleaning exercise - unlike `ml/generate_dataset.py`'s
   synthetic usage data, which has no real-world messiness to clean.

## Source

[UT1 Blacklists](http://dsi.ut-capitole.fr/blacklists/index_en.php),
maintained by Fabrice Prigent at Universite Toulouse Capitole. This is a
long-running, real project used by actual schools/universities for web
filtering - domains are manually reviewed and categorized, not generated.
Mirrored daily at [github.com/olbat/ut1-blacklists](https://github.com/olbat/ut1-blacklists),
licensed CC BY-SA 4.0 (attribution required, which this README provides).

Raw files in `raw/` were fetched directly from that mirror on the date
this was built (see git log for the exact date) and are committed
unmodified, so the "before cleaning" state is reproducible and verifiable
against the source.

### Categories included, and why

| UT1 category | Rows (raw) | Maps to |
|---|---|---|
| `gambling` | 32,247 | Table 6 "harmful website/category" |
| `drogue` (renamed `drugs` here) | 603 | Table 6 "harmful website/category" |
| `dangerous_material` | 35 | weapons/explosives instructions; also includes a couple of pro-eating-disorder domains, which are self-harm-adjacent |

**Deliberately excluded:** UT1's `adult` category (4.6 million domains -
not practical to store or ship as a mobile asset for a school project, and
not needed to demonstrate the cleaning methodology). A production version
would add it from the same source, the same way.

**Honest gap:** UT1 has no dedicated self-harm/suicide category. That
part of Table 6's indicator isn't covered by this dataset. A keyword-based
approach (similar to `PatternDetectionService`'s existing `riskyKeywords`
list, which already does rule-based text matching) is a more realistic
path for that specific risk than a domain blocklist, since self-harm
content usually shows up on mainstream sites/forums rather than
dedicated, blockable domains. Not built here - flagged for a future
session.

## Cleaning methodology

`clean_dataset.py` runs these steps on each raw category file, in order,
and logs the result of every step:

1. Strip whitespace, drop blank lines and comment lines (`#`, `//`).
2. Take only the first whitespace-separated token per line (guards
   against stray trailing comments on a data line).
3. Detect and remove entries that are IP addresses rather than domain
   names (`ipaddress` stdlib) - a blocklist keyed on domain name can't
   match against a bare IP the same way, so these need separate handling
   this project doesn't do yet, and are logged rather than silently kept.
4. Validate the remaining tokens against a permissive FQDN pattern;
   anything that doesn't look like a real domain is rejected and logged.
5. Deduplicate within each category.
6. Deduplicate across categories (a domain listed under more than one raw
   file keeps its first-encountered category; every conflict is logged
   rather than dropped silently).

Every count above is real output from running the script against the
actual raw files, not estimated. Full numbers are in
`output/cleaning_report.txt`, regenerated each run.

### What the cleaning actually found

Run against the current raw files: 181 of 32,885 raw rows (0.6%) were
removed, almost entirely IP-address entries mixed into what's supposed to
be a domain-only list - 14 in `gambling`, 167 in `drogue`/`drugs` (about
28% of that file). Zero malformed entries and zero duplicates turned up in
either file, and zero domains overlapped across the three categories.
That's a legitimate finding, not a shortcoming of the cleaning script: UT1
is a mature, actively-maintained project, so its lists arrive fairly
clean already. The real, demonstrable data-quality issue this pipeline
catches and fixes is the IP-vs-domain mixing.

**Known limitation worth flagging in your Results/Limitations section:**
the final dataset is heavily imbalanced - `gambling` is 32,233 of 32,704
rows (98.6%), `drugs` 436, `dangerous_material` only 35. If this ever
trains a real text/lexical classifier (as opposed to a straight lookup
table), that imbalance needs addressing (e.g. class weighting, same as
`train_model.py` already does for the usage-risk model). For a pure
domain-lookup implementation, the imbalance doesn't matter - the app
checks against the whole list regardless of category size.

## Reproducing this

```bash
cd ml/site_category
python3 clean_dataset.py
```

Deterministic given the same raw files - no randomness involved, unlike
`ml/generate_dataset.py`.

## What's NOT done yet (deferred, per project decision)

- ~~Reading the address bar / current URL from the browser via the Android
  accessibility service~~ - **done**, see `BrowserUrlExtractor.kt` and
  `WellScreenAccessibilityService.kt`.
- ~~Wiring the cleaned dataset into the app and matching captured domains
  against it~~ - **done**, see `mobile_app/lib/services/
  site_category_service.dart` (bundled as
  `mobile_app/assets/site_categories/cleaned_site_categories.csv`) and
  its use in `child_home_screen.dart`'s `syncUsageReport()`. A match
  tags the entry and sends the parent a push alert (see
  `alerts_reports_screen.dart`'s "Recent Browsing Activity" and
  "Category-Level Detection" cards). **Still not real-time blocking** -
  the page has already loaded by the time this runs (at next sync, in
  Dart); preventing the load would need the same check running natively
  in Kotlin before the page renders, which isn't built.
- A self-harm-specific detection path (see "Honest gap" above).
- Including the `adult` category, or updating this dataset as UT1's lists
  change (their site updates daily; this is a snapshot).
- Capture is currently limited to `TYPE_WINDOW_STATE_CHANGED` /
  `TYPE_WINDOWS_CHANGED` events (see `maybeCaptureBrowserUrl()`'s doc
  comment) - reliable for full page loads/new tabs, but can miss
  same-page navigation that doesn't trigger a window-state change.
